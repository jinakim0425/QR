# 도메인 클래스 구조 설계

**프로젝트명** QR 기반 공용기자재 예약·반납 시스템

**작성자** 김진아

**작성일** 2026-09-08

**버전** v1.0

<br>

## 1. 문서 목적

서비스 흐름에서 도출된 핵심 개념을 도메인 클래스로 정의하고,
클래스 간의 관계와 주요 속성을 정리하여 이후 ERD 설계 및 구현의 기준을 마련한다.

<br>

## 2. 클래스 목록

| 클래스 | 역할 |
| --- | --- |
| Member (회원) | 서비스를 이용하는 사용자 정보와 권한을 관리한다 |
| Item (물품) | 공용기자재의 정보와 보유 수량을 관리한다 |
| Rental (대여) | 회원이 물품을 대여한 한 건의 기록을 관리한다 |
| Reservation (예약) | 회원이 물품을 선점한 한 건의 기록을 관리한다 |

<br>

## 3. 클래스별 속성

### 3.1 Member (회원)

| 속성 | 타입 | 설명 |
| --- | --- | --- |
| memberId | Long | 회원 식별자 (PK) |
| name | String | 회원 이름 |
| phone | String | 연락처 |
| password | String | 로그인 비밀번호 |
| role | Role | 권한 구분 (USER / ADMIN) |
| createdAt | LocalDateTime | 가입 일시 |

### 3.2 Item (물품)

| 속성 | 타입 | 설명 |
| --- | --- | --- |
| itemId | Long | 물품 식별자 (PK) |
| name | String | 물품명 (독서대, 담요, 충전기, 보조배터리 등) |
| description | String | 물품 설명 |
| totalQuantity | int | 총 보유 수량 |
| availableQuantity | int | 현재 대여 가능한 잔여 수량 |
| qrCode | String | 물품 식별용 QR 코드 값 |
| returnLocation | String | 반납 장소 |

### 3.3 Rental (대여)

| 속성 | 타입 | 설명 |
| --- | --- | --- |
| rentalId | Long | 대여 식별자 (PK) |
| member | Member | 대여한 회원 (FK) |
| item | Item | 대여한 물품 (FK) |
| rentedAt | LocalDateTime | 대여 일시 |
| dueAt | LocalDateTime | 반납 예정 일시 |
| returnedAt | LocalDateTime | 실제 반납 일시 (미반납 시 null) |
| status | RentalStatus | 대여 상태 (대여중 / 연체 / 반납완료) |

### 3.4 Reservation (예약)

| 속성 | 타입 | 설명 |
| --- | --- | --- |
| reservationId | Long | 예약 식별자 (PK) |
| member | Member | 예약한 회원 (FK) |
| item | Item | 예약한 물품 (FK) |
| reservedAt | LocalDateTime | 예약 일시 |
| expiresAt | LocalDateTime | 예약 만료 일시 |
| status | ReservationStatus | 예약 상태 (예약중 / 수령완료 / 취소 / 만료) |

## 4. 클래스 관계

```
                 ┌──────────┐
                 │  Member  │
                 └────┬─────┘
                 1    │    1
            ┌─────────┴─────────┐
            │ N               N │
      ┌─────▼─────┐       ┌─────▼───────┐
      │  Rental   │       │ Reservation │
      └─────▲─────┘       └─────▲───────┘
            │ N               N │
            └─────────┬─────────┘
                 1    │    1
                 ┌────┴─────┐
                 │   Item   │
                 └──────────┘
```

| 관계 | 카디널리티 | 설명 |
| --- | --- | --- |
| Member — Rental | 1 : N | 한 회원은 여러 건을 대여할 수 있으며, 반납 후에도 이력이 남는다 |
| Item — Rental | 1 : N | 한 물품은 여러 회원에게 반복적으로 대여된다 |
| Member — Reservation | 1 : N | 한 회원은 여러 건의 예약을 가질 수 있다 |
| Item — Reservation | 1 : N | 한 물품에 대해 여러 예약이 존재할 수 있다 |

<br>

## 5. 설계 의사결정

### 5.1 대여를 독립 클래스로 분리

대여 정보를 회원 클래스의 속성으로 포함시키는 방안을 검토했으나,
한 회원이 여러 건을 동시에 대여할 수 있고 반납 이후에도 이력이 보존되어야 하므로
대여를 독립 클래스로 분리하고 회원과 1:N 관계로 설계하였다.

### 5.2 예약과 대여의 분리

예약과 대여를 하나의 클래스로 통합하는 방안을 검토했으나 다음 차이로 인해 분리하였다.

| 구분 | 예약 | 대여 |
| --- | --- | --- |
| 물품 점유 여부 | 선점만 하며 실물은 보유하지 않음 | 실물을 보유함 |
| 종료 조건 | 수령 / 취소 / 만료 | 반납 |
| 시간 기준 | 만료 시각까지 유효 | 반납 기한까지 유효 |

두 개념은 상태 전이 방식과 종료 조건이 서로 달라 하나의 상태 값으로 표현할 경우
상태가 지나치게 복잡해진다고 판단하였다.

### 5.3 잔여 수량의 관리 방식

잔여 수량을 대여 기록에서 매번 집계하여 계산하는 방안과
물품 클래스에 속성으로 유지하는 방안을 비교하였다.

- 집계 방식: 데이터 정합성이 높으나 조회 시마다 연산이 필요하다
- 속성 유지 방식: 조회 성능이 우수하나 대여·반납 시 갱신 누락 위험이 있다

메인 화면에서 실시간 잔여 수량 조회가 가장 빈번한 요청이라는 점을 고려하여
물품 클래스에 `availableQuantity` 속성으로 유지하되,
대여·반납·예약 처리를 하나의 트랜잭션으로 묶어 정합성을 보장하는 방식으로 결정하였다.

## 6. 열거형 정의

| 열거형 | 값 |
| --- | --- |
| Role | USER, ADMIN |
| RentalStatus | RENTED(대여중), OVERDUE(연체), RETURNED(반납완료) |
| ReservationStatus | RESERVED(예약중), PICKED_UP(수령완료), CANCELED(취소), EXPIRED(만료) |
